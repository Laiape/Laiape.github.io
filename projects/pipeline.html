A fully procedural, data-driven rigging system built in Maya Python. Given a set of guide locators, it builds a complete character rig from scratch — joints, controllers, IK/FK systems, space switches, and skin weights — without any manual scene state. Every build starts from a blank scene. The rig is deterministic: the same guides always produce the same rig.

Built to produce rigs for O'Paraiso and all future characters, the toolkit is now the foundation of my production pipeline.

01 — Architecture

PIPELINE
MODULES

The system is broken into five independent modules. Each is responsible for one stage of the build. Modules communicate through a JSON cache on disk — not through Python memory — so each build is reproducible and scene-state independent.

01
Asset Management

Tracks the active character via Maya's optionVar — persists across cmds.file(new=True) calls. On first setup it generates the full folder structure: models/, build/, guides/, curves/, skin_clusters/. Every build opens a clean scene from assets/<char>/models/ — no carried state from previous sessions.

optionVar File I/O Scene Management
02
Guides & Skeletons

Guides are locators placed in T-pose — the only persistent artist input. They are mirrored automatically from L_ to R_, then exported to JSON. The rig is rebuilt entirely from that file each build. Data-driven: if a guide exists, that limb is built. If it doesn't, it's skipped. One pipeline supports biped, quadruped, and facial in the same system.

JSON export Auto mirror Data-driven T-pose
03
Curves & Controllers

Controller shapes are stored per character as a .curves JSON file — CV positions, knots, degree, form, override color, alwaysDrawOnTop. At build time the system recreates each curve via Maya API 2.0. Color convention: cyan for Left, blue for Right, yellow for Center. Mirror uses scaleX = -1 + makeIdentity — one operation, any shape.

.curves format API 2.0 Color system Auto mirror
04
Skin Clusters

Custom .skc sparse format stores only non-zero weights — 60–80% smaller than Maya's native export. Auto-transfer via skeleton-relative UV projection: vertices from both characters are mapped into a shared coordinate space defined by their shared skeleton. Works across different topology, vertex count, and proportions. The source character doesn't need to be in the scene at build time.

.skc sparse UV projection KNN + IDW Topology-independent
05
Rig Functionality & Logic

The entire constraint system uses matrix nodes only — multMatrix, blendMatrix, parentMatrix, offsetParentMatrix. No parentConstraint or orientConstraint. IK/FK blend is driven by blendMatrix feeding into offsetParentMatrix. Space switches use parentMatrix + blendMatrix + condition nodes, with enum attributes directly on the controller. Modules communicate through a JSON cache bus — each module registers its output node names, and space switches resolve in post-build without depending on module execution order.

multMatrix blendMatrix offsetParentMatrix IK/FK blend Space switches JSON bus
02 — Build

BUILD
SEQUENCE

The full rig is rebuilt from scratch every time — no incremental updates, no persistent scene state. Eight steps, always in the same order.

# 1. Clear cache & set character context data_manager.DataExportBiped().new_build() # 2. Build group hierarchy + master controllers basic_structure.create_basic_structure() # 3. Load guides → build joints → IK/FK → controllers → matrix constraints rig_manager.build_rig(char_name) # 4. Label joints for game export (L/R/C + otherType) create_rig.label_joints() # 5. Hide intermediate nodes from Outliner create_rig.hide_connections() # 6. Disable inheritsTransform on all controllers create_rig.inherit_transforms() # 7. Apply stored skin weights (.skc sparse format) skin_manager_api.SkinManager().import_skins() # 8. Auto-transfer if no .skc found (topology-independent) # → runs only for meshes with no weights after step 7
03 — Design

WHY THESE
DECISIONS

Why matrix nodes instead of Maya constraints?
Matrix operations are evaluated in parallel by Maya's dependency graph. parentConstraint nodes add evaluation overhead and clutter the DAG. Matrix nodes are cleaner, faster, and produce rigs that export to game engines without extra cleanup.
Why rebuild from scratch every build?
Incremental builds accumulate state — a fix in one session can break something in the next. Rebuilding from scratch guarantees that the rig always matches the guides. The artist's only persistent input is the guide file and the curves file, both of which are version-controlled.
Why skeleton-relative UV for skin transfer?
Point-cloud matching breaks when two characters have different proportions. The skeleton defines body regions that are consistent regardless of mesh density or scale. Mapping vertices into skeleton-relative coordinates means a hip joint always maps to the hip area, even if one character is twice as wide.
Why a JSON cache bus between modules?
Python memory doesn't survive scene reloads or importlib.reload() calls. A file on disk does. The cache also acts as a build log — opening biped.cache immediately shows which modules ran, what node names were assigned, and where space switches will connect.
